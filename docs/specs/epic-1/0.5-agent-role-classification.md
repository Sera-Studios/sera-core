# Spec 0.5: Agent Role Classification

**Status:** Complete
**Epic:** 1 - Resource & Role Management
**Depends on:** None

## Overview

Add a first-class `roles` field to `AgentRegistration` that distinguishes execution agents (do work, produce deliverables) from evaluation agents (assess deliverables, produce metrics). An agent can have both roles - e.g., a judge agent is an evaluation agent when assessing hunter findings, but an execution agent when being benchmarked for verdict accuracy. This is needed by the benchmarker-dashboard to determine which agents are available for each phase of a benchmark run.

## Problem

`AgentRegistration` has no concept of agent role. The benchmarker currently infers agent type from naming conventions (`judge-` prefix) or optional `metadata.agentType`. This is fragile - there's no authoritative source for "is this an execution agent or an evaluation agent?"

The benchmarker needs to query sera-core for "all execution agents" when setting up the work phase, and "all evaluation agents" when setting up the evaluation phase. Today that query doesn't exist.

## Solution

Add `roles: AgentRole[]` to `AgentRegistration` in `@sera/types`. An agent can have one or both roles. Update sera-core's registration store and list endpoints to support filtering by role.

## Design

### Type Change

In `packages/sera-types/src/agent.ts`, add `roles` to `AgentRegistration`:

```typescript
export type AgentRole = 'execution' | 'evaluation';

export interface AgentRegistration {
    id: string;
    name: string;
    version: string;
    description: string;
    roles: AgentRole[];            // <-- new field
    execution: ExecutionConfig;
    interface: AgentInterface;
    metadata?: { ... };
    defaultTimeout: number;
    requiredCredentials?: RequiredCredential[];
}
```

Examples:
- Hunter: `roles: ['execution']` - only produces findings
- Judge: `roles: ['execution', 'evaluation']` - produces verdicts (execution) and evaluates findings (evaluation)
- Verdict scorer script: `roles: ['evaluation']` - only scores verdicts

Default: `['execution']`. Existing registrations without a `roles` field are treated as execution-only during deserialization.

### Registration Store

In `AgentRegistrationStore.ts`, when loading JSON files from `~/.sera/agents/`:

```typescript
// Backward compat: default missing roles to ['execution']
const registration = JSON.parse(content);
if (!registration.roles) registration.roles = ['execution'];
```

Add filtering method:

```typescript
/** Get registrations that include a specific role */
getByRole(role: AgentRole): AgentRegistration[] {
    return this.getAll().filter(r => r.roles.includes(role));
}
```

### REST API Filter

`GET /api/agents/registrations` gains an optional query parameter:

```
GET /api/agents/registrations?role=evaluation
GET /api/agents/registrations?role=execution
```

When `role` is provided, return agents whose `roles` array includes that value. When omitted, return all (current behavior). A judge agent with `roles: ['execution', 'evaluation']` appears in both filtered results.

### MCP Tool Update

`list_agent_registrations` gains an optional `role` input:

```typescript
{
    name: 'list_agent_registrations',
    inputSchema: {
        type: 'object',
        properties: {
            role: {
                type: 'string',
                enum: ['execution', 'evaluation'],
                description: 'Filter to agents that include this role'
            }
        }
    }
}
```

Response includes the `roles` field in each summary entry.
